### Arguments

| Tag | Listener value | Proof used in the talk |
|---|---|---|
| **Clear reasoning** | The receiver understands the concern and has a next step. | A hypothetical pull-request comment is rewritten from “This is wrong” into a risk, reason and question. |
| **Shared problem** | Developers can challenge work without judging the person. | A concrete notice–effect–next-step example replaces a personal verdict. |
| **Deliberate practice** | Developers gain language they can use when a conversation becomes tense. | Ask, give and receive examples demonstrate better next sentences. |

### Elephant in the room

“I already review code. This sounds like soft-skills common sense.”

Park it by opening inside a familiar pull request, contrasting two practical comments, avoiding unsupported performance claims and making the first step a free workshop on a specific date.

## Structure options considered

1. **Monroe’s Motivated Sequence — selected.** Best fit for moving a meetup audience from recognition to immediate signup.
2. **Sparkline.** Alternate repeatedly between vague verdicts and useful feedback, ending with the workshop. Strong visually, but less direct about the action.

## Chosen structure and timing

| Stage | Time | Content |
|---|---:|---|
| Attention | 0:00–0:37 | A developer opens a pull request and sees “This is wrong.” |
| Need | 0:37–1:23 | Code review is already a feedback conversation; vague feedback hides reasoning. |
| Solution | 1:23–3:18 | Make the work a shared problem and practise the next sentence. |
| Visualization | 3:18–3:44 | A review becomes shared debugging instead of tone decoding. |
| Action | 3:44–4:21 | Repeat the three tags and invite an immediate workshop signup. |
| Buffer | 4:21–5:00 | Room response, slower delivery or transition to the next speaker. |
